# NanoASR

[English](README.md) · **Русский**

Оффлайн-сервер распознавания речи на [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx).
Один бинарь, инференс на CPU, пословные тайминги, три диалекта HTTP API и встроенный
веб-интерфейс.

Сервис рассчитан на пакетную обработку файлов: записи разговоров, интервью, совещаний
длиной от одной минуты до получаса, моно и стерео, включая телефонные 8 кГц. Ни один
байт аудио не покидает машину — модели работают локально, сетевой доступ нужен только
для первичной загрузки весов.

## Архитектура

Запрос проходит фиксированный конвейер. Каждый этап измеряется отдельно и попадает в
`stats.stages_ms` ответа.

```
                                  ┌──────────────┐
файл ──► decode ──► vad ──► asr ──►   assemble   ──► diarize ──► post ──► результат
         │          │       │      │              │   │           │
    ffmpeg или  Silero  sherpa-onnx  токены     Sortformer    пунктуация,
    нативный    VAD v5  батчами по   в слова    или sherpa    ITN, hotwords
    WAV/PCM             сегментам    с таймингами
```

| Этап | Назначение |
|---|---|
| `decode` | Определение формата, декодирование, приведение к 16 кГц, обработка каналов |
| `vad` | Разбиение на сегменты речи, вычисление зон тишины |
| `asr` | Распознавание сегментов батчами под управлением CPU-губернатора |
| `assemble` | Сборка токенов в слова с границами по времени |
| `diarize` | Определение говорящих и нарезка сегментов по границам реплик |
| `post` | Пунктуация, инверсная нормализация текста |

Ключевые свойства реализации:

- **Единая точка входа.** Вся бизнес-логика находится за интерфейсом `core.Service`.
  Диалекты API преобразуют формы запроса и ответа и не имеют доступа к пулу моделей,
  реестру или очереди. Добавление диалекта — один пакет, регистрирующий себя в `init()`.
- **Пул моделей.** Резидентные экземпляры с подсчётом ссылок, вытеснением по LRU и
  горячей заменой ревизии без разрыва выполняющихся запросов.
- **CPU-губернатор.** Число одновременно исполняемых батчей ограничено взвешенным
  семафором, чтобы параллельные запросы не деградировали до нуля пропускной способности.
- **Очередь задач.** SQLite (чистый Go, без cgo) для метаданных, файловый спул для
  аудио, приоритеты, возобновление после рестарта, поток событий по SSE, вебхуки с
  подписью HMAC.
- **Один артефакт.** Веб-интерфейс встраивается в бинарь на этапе компиляции.

## Возможности

**Распознавание**

- Пословные тайминги с достоверностью для каждого слова.
- Семейства моделей: `nemo_ctc`, `zipformer_ctc`, `wenet_ctc`, `transducer`, `telespeech`.
- Батчинг сегментов с ограничением по числу и суммарной длительности.
- Выбор модели на запрос; параллельная резидентность нескольких моделей.
- Методы декодирования `greedy_search` и `modified_beam_search`.
- Смещение распознавания в пользу заданных слов (hotwords).
- Потоковое распознавание по websocket, пока аудио ещё идёт: промежуточные гипотезы
  и автоматические границы фраз.
- CPU или NVIDIA GPU — одна настройка, проверяемая при старте, а не молчаливый
  откат на процессор.

**Аудио**

- WAV и сырой PCM декодируются в процессе, без внешних зависимостей: 16/24/32 бита,
  float32, a-law и µ-law.
- Все остальные форматы — через ffmpeg, который остаётся опциональным.
- Полифазный ресемплер до 16 кГц.
- Три режима обработки каналов: сведение, первый канал, раздельное распознавание.

**Результат**

- Текст, сегменты, слова, зоны тишины, говорящие, доля речи, статистика по этапам.
- Форматы ответа: JSON, обычный текст, SRT, VTT, TSV.
- Субтитры с метками говорящих.

**Постобработка**

- Пунктуация и регистр: от модели распознавания либо отдельной моделью пунктуации.
- Инверсная нормализация текста для русского языка: числа, даты, время, деньги,
  телефоны, проценты.
- Диаризация: определение говорящих, пословная привязка, нарезка сегментов по репликам.

**Эксплуатация**

- Четыре диалекта HTTP API одновременно на одном порту, один из них — websocket.
- Справочник по API на `/docs`: собирается из реально подключённых диалектов и
  отдаётся без ключа.
- Аутентификация по ключам API с ограничением частоты запросов и приоритетами.
- Реестр моделей: встроенный каталог, загрузка с проверкой SHA-256, управление через API.
- Автоматический подбор размеров пулов по числу ядер и объёму памяти.
- Проверки `/healthz` и `/readyz`, отражающие глубину очереди.

## Установка

### Одной командой

Linux, служба systemd. По умолчанию распознавание на CPU; `--gpu` переводит его на
NVIDIA, `--addr` задаёт адрес и порт:

```bash
# CPU, на 127.0.0.1:8080.
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash

# NVIDIA GPU, CUDA 12 или 13 с cuDNN 9. Та же установка, но на устройстве.
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash -s -- --gpu

# Свой порт, доступный с других машин.
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash -s -- --addr 0.0.0.0:9000

# И то и другое.
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash -s -- --gpu --addr 0.0.0.0:9000
```

Windows, служба, в PowerShell. Установка и проверка GPU пока только для Linux, так что
здесь остаётся выбрать адрес — а `iex` не умеет передавать аргументы, поэтому он
приходит переменной окружения:

```powershell
# CPU, на 127.0.0.1:8080.
irm https://github.com/usunrise88/NanoASR/releases/latest/download/install.ps1 | iex

# Свой порт.
$env:NANOASR_ADDR = "0.0.0.0:9000"; irm https://github.com/usunrise88/NanoASR/releases/latest/download/install.ps1 | iex
```

Каждый из скриптов определяет последний релиз, сверяет загруженное с опубликованным
`sha256sums.txt`, распаковывает архив, пишет конфигурацию с двумя ключами API,
загружает модели по умолчанию и оставляет работающую службу; ключи и адрес выводятся в
конце. Повторный запуск — это обновление на месте: служба сначала останавливается,
конфигурация и модели сохраняются.

«Сохраняются» стоит понимать буквально, и это важно знать, передавая флаг обновлению:
параметры, которые доезжают до `nanoasr init` — адрес прослушивания, `--realtime` —
применяются только когда конфигурации ещё нет. При обновлении решает файл, установщик
говорит, какой флаг он не применил, а правка — это одна строка в конфигурации (или, для
адреса, `systemctl edit` и `Environment=NANOASR_ADDR=...` только для службы).

| | Linux | Windows |
|---|---|---|
| Бинарь и библиотеки | `/opt/nanoasr` | `C:\Program Files\NanoASR` |
| Конфигурация, модели, база задач | `/var/lib/nanoasr` | `C:\ProgramData\NanoASR` |
| Служба | `systemctl status nanoasr` | `Get-Service NanoASR` |
| Журнал | `journalctl -u nanoasr -f` | `C:\ProgramData\NanoASR\logs\nanoasr.log` |

Ни один из скриптов ничего не меняет, пока не проверит то, что может проверить:
архитектуру, glibc против musl, запущен ли systemd, права администратора. В Windows
скрипт сам запрашивает повышение прав и продолжает работу в окне, где они есть; в Linux
привилегированные шаги выполняются через `sudo` по одному — скрипту, пришедшему по
конвейеру, нечего перезапускать от имени root. ffmpeg устанавливается, если его нет, а
система предлагает очевидный способ: без него принимаются только WAV и сырой PCM.

Каждый параметр — флаг, и у каждого флага есть переменная окружения: она нужна там,
где аргументы передать нельзя.

```bash
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash -s -- --addr 0.0.0.0:8080
NANOASR_ADDR=0.0.0.0:8080 curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash
```

```powershell
$env:NANOASR_ADDR = "0.0.0.0:8080"
irm https://github.com/usunrise88/NanoASR/releases/latest/download/install.ps1 | iex
```

| Linux | Windows | Переменная | |
|---|---|---|---|
| `--version TAG` | `-Version TAG` | `NANOASR_VERSION` | установить конкретный релиз |
| `--addr HOST:PORT` | `-Addr HOST:PORT` | `NANOASR_ADDR` | адрес прослушивания, по умолчанию `127.0.0.1:8080` |
| `--prefix DIR` | `-Prefix DIR` | `NANOASR_PREFIX` | куда кладётся бинарь |
| `--data-dir DIR` | `-DataDir DIR` | `NANOASR_DATA_DIR` | куда кладутся модели и база задач |
| `--no-ui` | `-NoUI` | `NANOASR_UI=0` | сборка без веб-интерфейса |
| `--no-download` | `-NoDownload` | `NANOASR_DOWNLOAD=0` | написать конфигурацию, модели не загружать |
| `--no-ffmpeg` | `-NoFfmpeg` | `NANOASR_FFMPEG=0` | не трогать ffmpeg |
| `--realtime` | `-Realtime` | `NANOASR_REALTIME=1` | плюс потоковое распознавание по websocket |
| `--gpu` | — | `NANOASR_GPU=1` | распознавание на NVIDIA GPU (Linux); `--no-gpu` — обратно |
| `--no-start` | `-NoStart` | `NANOASR_START=0` | установить всё, ничего не запускать |
| `--uninstall` | `-Uninstall` | `NANOASR_UNINSTALL=1` | остановить и удалить установку |
| `--purge` | `-Purge` | `NANOASR_PURGE=1` | вместе с предыдущим — удалить и данные |

`--help` и `-Help` перечисляют остальное. Удаление сохраняет каталог данных — модели,
базу задач и спул, — если не добавлен `--purge`:

```bash
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash -s -- --uninstall
```

```powershell
$env:NANOASR_UNINSTALL = 1
irm https://github.com/usunrise88/NanoASR/releases/latest/download/install.ps1 | iex
```

Адрес, отличный от локального, в Windows понимается буквально: установщик открывает
этот порт TCP в брандмауэре и сообщает об этом. В Linux брандмауэр не затрагивается.

### Готовые сборки

Архивы публикуются на [странице релизов](https://github.com/usunrise88/NanoASR/releases).

| Файл | Платформа |
|---|---|
| `nanoasr-<tag>-linux-amd64.tar.gz` | Linux, веб-интерфейс включён |
| `nanoasr-<tag>-linux-amd64-noui.tar.gz` | Linux, без веб-интерфейса |
| `nanoasr-<tag>-windows-amd64.zip` | Windows, веб-интерфейс включён |
| `nanoasr-<tag>-windows-amd64-noui.zip` | Windows, без веб-интерфейса |

Веб-интерфейс встраивается на этапе компиляции, поэтому сборка без него — отдельный
бинарь, а не флаг запуска.

Нативные библиотеки (`libonnxruntime`, `libsherpa-onnx`) находятся внутри архива.
Архив следует распаковывать целиком: в Linux `RUNPATH` бинаря указывает на `./lib`,
в Windows загрузчик ищет DLL рядом с исполняемым файлом.

```bash
tar -xzf nanoasr-v1.1.0-linux-amd64.tar.gz -C ~/nanoasr
cd ~/nanoasr
```

### Служба systemd

То же самое делает `install.sh`; ниже — как сделать это вручную. Файл `nanoasr.service`
входит в состав Linux-архива. Разметка каталогов: бинарь и конфигурация в
`/opt/nanoasr`, модели, база задач и спул — в `/var/lib/nanoasr`.

```bash
sudo useradd -r -s /usr/sbin/nologin nanoasr
sudo mkdir -p /opt/nanoasr /var/lib/nanoasr
sudo tar -xzf nanoasr-v1.1.0-linux-amd64.tar.gz -C /opt/nanoasr
sudo chown -R nanoasr:nanoasr /opt/nanoasr /var/lib/nanoasr
```

Конфигурация, ключи и модели создаются от имени служебного пользователя, чтобы
загруженные файлы принадлежали ему:

```bash
sudo -u nanoasr /opt/nanoasr/nanoasr init \
  -config /opt/nanoasr/nanoasr.yaml \
  -data-dir /var/lib/nanoasr \
  -addr 127.0.0.1:8080 \
  -force
```

`-force` требуется потому, что архив уже содержит `nanoasr.yaml`. Оба выпущенных ключа
выводятся на экран; они же остаются в конфигурации.

```bash
sudo cp /opt/nanoasr/nanoasr.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now nanoasr
systemctl status nanoasr
```

Юнит запускает `nanoasr serve -config /opt/nanoasr/nanoasr.yaml` и применяет
`ProtectSystem=strict`: единственный каталог, доступный службе на запись, —
`/var/lib/nanoasr`. Конфигурация читается при старте, поэтому выпуск и отзыв ключей
требуют `systemctl restart nanoasr`.

Готовность проверяется по `/readyz`, а не по факту запуска процесса: загрузка весов
занимает секунды, а при заполненной очереди `/readyz` отвечает `503`. Причина отказа
запуска выводится в журнал:

```bash
journalctl -u nanoasr -n 50 --no-pager
```

### Служба Windows

То же самое делает `install.ps1`. Службу регистрирует сам бинарь, поэтому для установки
вручную ничего, кроме него, не нужно:

```powershell
nanoasr.exe init -config C:\ProgramData\NanoASR\nanoasr.yaml -data-dir C:\ProgramData\NanoASR
nanoasr.exe --install
```

`--install` создаёт службу, ставит её на автозапуск (с задержкой: она читает гигабайты
весов, и ничто её не ждёт), перезапускает при сбое через 5, 15 и 60 секунд и запускает.
Конфигурацию, с которой сервер не стартует, он регистрировать отказывается — в
`nanoasr.yaml` из архива ключей нет, а служба, которая устанавливается, стартует и тут
же завершается, нигде себя не объясняет, — и печатает команду `init`, которая пишет
рабочую.

| | |
|---|---|
| `nanoasr --install` | зарегистрировать и запустить: `-config FILE`, `-log-file FILE`, `-name NAME`, `-manual`, `-no-start`, `-account`, `-password` |
| `nanoasr --uninstall` | остановить и удалить службу; конфигурация, модели и база остаются |
| `nanoasr --start`, `--stop`, `--restart` | как называются |
| `nanoasr --status` | состояние, идентификатор процесса, тип запуска, учётная запись и зарегистрированная командная строка |

У каждой команды есть и форма `nanoasr service install`. Всё, кроме `--status`, меняет
диспетчер служб и требует PowerShell с правами администратора; команда говорит об этом
сама, а не падает с ошибкой доступа тремя уровнями ниже. Повторный `--install` поверх
существующей службы обновляет её на месте — это то, что нужно при переезде в новый
каталог.

У службы Windows нет консоли, поэтому всё, что сервер пишет в стандартный поток ошибок,
пропадает. Служба всегда регистрируется с `-log-file`, по умолчанию
`C:\ProgramData\NanoASR\logs\nanoasr.log`; файл ротируется на 64 МБ и хранит одно
предыдущее поколение. Причина, по которой служба завершилась, записывается туда до
выхода процесса.

Служба работает от LocalSystem, если `-account` не называет другую учётную запись — у
неё уже должно быть право «Вход в качестве службы», эта команда его не выдаёт.

### Docker


Образ содержит ffmpeg и нативные библиотеки. Веса моделей хранятся в томе

### NVIDIA GPU

Разница между распознаванием на CPU и на GPU — не в исполняемом файле, а в том, какую
сборку библиотек sherpa-onnx найдёт динамический загрузчик. Их публикуют две: против
onnxruntime только для CPU и против CUDA-сборки. NanoASR поставляется с первой, а
установщик подставляет вторую по ключу:

```bash
# Новая установка или уже работающая на CPU — команда одна и та же,
# потому что установка обновляется на месте.
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash -s -- --gpu

# И обратно.
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash -s -- --no-gpu
```

На существующей установке это скачает релиз, сохранит конфигурацию и модели, а потом
поставит GPU-библиотеки. CPU — значение по умолчанию, и **обновление никогда не меняет
того, на чём вы работаете**: установка, уже использующая GPU, его сохраняет, а её
библиотеки обновляются под новый бинарник — это важно, потому что в них зашита версия
sherpa-onnx, с которой он собран.

`scripts/install-gpu.sh` — тот же шаг отдельно и с дополнительными опциями
(`--cuda 13`, `--sherpa`, `--sha256`, `--revert`); `install.sh --gpu` запускает его за
вас. Скрипт скачивает CUDA-сборку ровно тех версий sherpa-onnx и onnxruntime, которые
сообщает установленный бинарник, проверяет измеренную контрольную сумму, распаковывает
библиотеки в `/opt/nanoasr/lib-gpu` и направляет службу на них через systemd drop-in,
который заодно выставляет `NANOASR_PROVIDER=cuda`. CPU-библиотеки остаются на месте —
поэтому возврат это удаление, а не переустановка.

Проверка идёт до переконфигурации: если библиотеки на этой машине загрузить нельзя —
нет драйвера, нет cuDNN, нет устройства — ничего не меняется, и служба продолжает
работать на процессоре.

Требования: Linux x86-64, драйвер NVIDIA, CUDA 12 и cuDNN 9 (`--cuda 13` для сборки
под CUDA 13). На Windows пока только CPU: CUDA-сборка sherpa-onnx для Windows
публикуется, но NanoASR её не ставит и не проверяет — проверка ниже читает `/proc`, —
поэтому `asr.provider: cuda` там отклоняется, а не игнорируется молча.

В контейнере это тот же образ с другим аргументом сборки:

```bash
docker build -f deploy/Dockerfile --build-arg FLAVOUR=gpu -t nanoasr:gpu .
docker run --gpus all -e NANOASR_AUTH_KEYS=sk-... -p 8080:8080 nanoasr:gpu
# или: docker compose -f deploy/docker-compose.yml --profile gpu up --build nanoasr-gpu
```

GPU здесь нужен ради пропускной способности, а не ради задержки одного потока.
Realtime-движок декодирует все открытые сессии одним батчем — именно это загружает
устройство; один поток 16 кГц просит несколько миллисекунд работы раз в сто
миллисекунд и загрузить ускоритель не может. После запуска имеет смысл поднять
`realtime.max_sessions` и `asr.batch.max_size`.

Что бы ни было написано в конфигурации, `nanoasr gpu` сообщает, на что способны
загруженные библиотеки:

```
$ nanoasr gpu
sherpa-onnx   1.13.6
onnxruntime   1.27.1
library dir   /opt/nanoasr/lib-gpu
providers     libonnxruntime_providers_cuda.so libonnxruntime_providers_shared.so
cuda provider /opt/nanoasr/lib-gpu/libonnxruntime_providers_cuda.so
nvidia driver 550.54.14
devices       /dev/nvidia0
runtime       cuda ready (driver 550.54.14, 1 device(s))
provider      cuda (from /opt/nanoasr/nanoasr.yaml)
verdict       cuda can be served
```

Те же проверки сервер делает при старте и отказывается запускаться, если
запрошенный провайдер обслужить нельзя. Это сделано намеренно: onnxruntime на запрос
недоступного провайдера пишет строку, которую никто не читает, и считает на CPU —
то есть сервер, которому велели использовать GPU, поднялся бы «здоровым» и работал
бы в разы медленнее, чем планировалось.

`asr.provider` действует на распознавание — офлайновое и потоковое, — на модель
пунктуации и на бэкенд диаризации `sherpa`. Две вещи остаются на процессоре при любой
настройке:

- VAD: Silero — это 1,5 МБ и решение по кадру в 32 мс, так что на пересылку данных
  ушло бы больше, чем на саму арифметику.
- Бэкенд диаризации `sortformer`, который используется по умолчанию: он создаёт свои
  сессии onnxruntime и не добавляет к ним провайдер, поэтому считает на CPU.
  Перенести его — это правка в `internal/diarize/sortformer`, и делать её без
  устройства, на котором можно измерить результат, не стоит.

### Обновление

Веса моделей, база задач и спул лежат в каталоге данных и переживают обновление любым
из способов. Версию после обновления показывает `nanoasr version` и ответ `/healthz`.

**Одной командой.** Повторный запуск установщика — это обновление: он останавливает
службу, заменяет бинарь и библиотеки, сохраняет конфигурацию и модели и запускает
службу снова.

```bash
curl -fsSL https://github.com/usunrise88/NanoASR/releases/latest/download/install.sh | bash
```

```powershell
irm https://github.com/usunrise88/NanoASR/releases/latest/download/install.ps1 | iex
```

**Архив и systemd.** Архив содержит собственный `nanoasr.yaml`, поэтому распаковка
поверх каталога перезаписала бы рабочую конфигурацию — её нужно исключить:

```bash
sudo systemctl stop nanoasr
sudo tar -xzf nanoasr-<новая версия>-linux-amd64.tar.gz -C /opt/nanoasr \
  --exclude=./nanoasr.yaml
sudo chown -R nanoasr:nanoasr /opt/nanoasr
sudo systemctl start nanoasr
```

Если в новой версии изменился файл юнита, его следует скопировать заново и выполнить
`systemctl daemon-reload`. Смена варианта сборки — с веб-интерфейсом или без — это то же
обновление: меняется только бинарь.

**Архив без systemd, включая Windows.** Остановить процесс, распаковать архив поверх
каталога, сохранив свою конфигурацию, запустить снова. В Windows следует заменить
`nanoasr.exe` и файлы `*.dll` вместе — библиотеки и бинарь версионируются совместно; а
если установка переехала, `nanoasr.exe --install` переводит службу на новое место.

**Docker.** Пересборка образа с сохранением тома данных:

```bash
docker compose -f deploy/docker-compose.yml up -d --build
```

Том `nanoasr-data` не пересоздаётся, поэтому веса моделей заново не загружаются.

**Сборка из исходников.**

```bash
git pull
make web build
```

Затем перезапустить процесс или службу. Если сервер установлен из архива, собранный
бинарь заменяется тем же способом, что и при обновлении из релиза.

## Быстрый старт

### Команда `init`

`nanoasr init` формирует рабочую конфигурацию, выпускает два ключа API и загружает
модели по умолчанию.

```bash
./nanoasr init
./nanoasr serve -config nanoasr.yaml
```

```
configuration  nanoasr.yaml
data           /var/lib/nanoasr

admin key      sk-nanoasr-...
user  key      sk-nanoasr-...
```

Каталог данных — `/var/lib/nanoasr`, если он доступен для записи, иначе
`./nanoasr-data`. Выбранный путь выводится на экран.

| Флаг | Назначение |
|---|---|
| `-config FILE` | Путь к создаваемой конфигурации, по умолчанию `nanoasr.yaml` |
| `-data-dir DIR` | Каталог моделей и базы данных |
| `-addr ADDR` | Адрес прослушивания, по умолчанию `127.0.0.1:8080` |
| `-model ID` | Модель распознавания по умолчанию |
| `-no-diarize` | Выключить диаризацию и не загружать её модель |
| `-no-download` | Только создать конфигурацию |
| `-force` | Перезаписать существующий файл конфигурации |

Конфигурация записывается и проверяется загрузчиком до начала скачивания весов, что
исключает появление файла, который сервер откажется читать.

### Ключи API

```bash
nanoasr key list                            # перечень ключей, секреты маскируются
nanoasr key issue ci -rps 5                 # выпуск ключа, секрет выводится в stdout
nanoasr key issue bot -hash                 # в конфигурацию попадает только sha256
nanoasr key issue ops -admin -interactive   # административный ключ вне общей очереди
nanoasr key remove ci                       # отзыв ключа
```

| Флаг | Назначение |
|---|---|
| `-admin` | Доступ к управлению моделями и конфигурацией |
| `-interactive` | Задачи ключа обслуживаются вне пакетной очереди |
| `-rps N` | Ограничение частоты запросов, `0` — без ограничения |
| `-hash` | Хранить только SHA-256; секрет выводится один раз |

Конфигурация редактируется как YAML-документ: комментарии, порядок ключей и
отсутствующие параметры сохраняются. Запись атомарна, результат проверяется до замены
файла. Ключи считываются при запуске, поэтому изменения применяются после перезапуска
сервера.

Режим `auth.mode: open` допускается только при прослушивании адреса обратной петли.
Режим `apikey` с пустым списком ключей приводит к отказу в запуске.

## Веб-интерфейс

Одностраничное приложение доступно на `/ui/` и включается параметром `ui.enabled`.
Ключ API запрашивается интерфейсом при первом ответе `401`.

| Раздел | Назначение |
|---|---|
| Распознавание | Загрузка файла, выбор модели и параметров, отслеживание прогресса |
| Результат | Плеер с подсветкой слова, фильтр по говорящему, поиск, экспорт |
| Задачи | История, статусы, фильтры, отмена, повторный просмотр результата |
| Модели | Каталог, загрузка весов, резидентность, закрепление, горячая замена |
| Настройки | Действующая конфигурация сервера в режиме чтения |

Интерфейс полностью работает поверх публичного API и не имеет собственных endpoint'ов.

## Поддерживаемые API

Диалекты включаются в конфигурации и обслуживаются одновременно:

```yaml
api:
  dialects: [openai, native, era, realtime]
```

`GET /docs` — справочник по тем из них, что действительно подключены: он собирается из
самих диалектов, а не пишется руками, и отдаётся без ключа — всё, что на нём есть, и
так известно любому, кто дотянулся до порта. `GET /` перенаправляет туда, а
`GET /docs/openapi.json` — тот же список эндпоинтов для генератора клиента (без схем
запросов и ответов, о чём там и написано).

### `native` — полный интерфейс сервиса

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/transcribe` | Синхронное распознавание |
| `POST` | `/api/v1/jobs` | Постановка задачи в очередь |
| `GET` | `/api/v1/jobs` | История с курсорной пагинацией |
| `GET` | `/api/v1/jobs/{id}` | Состояние и результат задачи |
| `GET` | `/api/v1/jobs/{id}/events` | Поток событий SSE |
| `DELETE` | `/api/v1/jobs/{id}` | Отмена задачи |
| `GET` | `/api/v1/models` | Резидентные и установленные модели |
| `GET` | `/api/v1/catalog` | Встроенный каталог моделей |
| `POST` | `/api/v1/models/{id}/download` | Загрузка весов, прогресс по SSE |
| `POST` | `/api/v1/models/{id}/load` | Загрузка модели в память |
| `POST` | `/api/v1/models/{id}/unload` | Выгрузка модели |
| `POST` | `/api/v1/models/{id}/pin` | Защита от вытеснения по LRU |
| `POST` | `/api/v1/models/{id}/reload` | Горячая замена ревизии |
| `GET` | `/api/v1/config` | Действующая конфигурация |

Управление моделями и конфигурацией требует административного ключа. Ошибки
возвращаются в формате RFC 9457 `application/problem+json`.

Параметры запроса: `model`, `language`, `response_format`, `channel_mode`,
`decoding_method`, `max_active_paths`, `diarize`, `num_speakers`, `punctuate`, `itn`,
`hotwords[]`, `hotwords_score`, `strict`, `webhook_url`.

Форматы ответа: `json`, `text`, `srt`, `vtt`.

### `openai` — совместимость с OpenAI Audio API

| Метод | Путь |
|---|---|
| `POST` | `/v1/audio/transcriptions` |
| `POST` | `/v1/audio/translations` |
| `GET` | `/v1/models` |
| `GET` | `/v1/models/{id}` |

Поддерживаются `file`, `model`, `language`, `prompt`, `response_format`,
`timestamp_granularities[]`. Форматы ответа: `json`, `verbose_json`, `text`, `srt`,
`vtt`. Ответ `verbose_json` дополнен полями `timestamp_source`, `silence`, `warnings`
и `stats`; клиенты OpenAI игнорируют неизвестные поля.

Отличия от оригинального API:

- `/v1/audio/translations` возвращает `501`: модели перевода не поставляются.
- `prompt` интерпретируется как список hotwords через запятую, а не как подсказка
  языковой модели.
- `temperature` принимается и не влияет на результат: декодеры не выполняют сэмплирование.

### `realtime` — потоковое распознавание по websocket

Распознавание, пока аудио ещё идёт, в протоколе событий OpenAI Realtime API с
`intent=transcription`.

| Метод | Путь |
|---|---|
| `GET` | `/v1/realtime?intent=transcription` (переход на websocket) |
| `POST` | `/v1/realtime/transcription_sessions` (`501` и объяснение, как подключаться) |

Нужна потоковая модель — это другой экспорт другой архитектуры, чем офлайновые
(энкодер обучен с правым контекстом в несколько сотен миллисекунд), поэтому диалект
включается осознанно:

```yaml
api:
  dialects: [openai, native, realtime]
realtime:
  model: t-one-ctc-ru
```

`nanoasr init -realtime` или `install.sh --realtime` пишут это и скачивают модель.

**События клиента.** `session.update` (принимается и `transcription_session.update`),
`input_audio_buffer.append` с аудио в base64, `input_audio_buffer.commit` и
`input_audio_buffer.clear`. Бинарный кадр websocket принимается как сырое аудио в
объявленном формате — это экономит треть трафика, которую стоит base64.

**События сервера.** `transcription_session.created` и `.updated`,
`input_audio_buffer.speech_started`, `.speech_stopped`, `.committed`, `.cleared`,
`conversation.item.created`,
`conversation.item.input_audio_transcription.delta` и `.completed`, `error`, а также
`nanoasr.warning` — о параметре, который принят и проигнорирован.

**Аудио.** `input_audio_format` принимает `pcm16` (по умолчанию 24 кГц, как в API
OpenAI), `g711_ulaw`, `g711_alaw` либо объект с частотой:

```json
{"type": "session.update",
 "session": {"input_audio_format": {"type": "audio/pcm", "rate": 16000}}}
```

Форма с объектом здесь важнее, чем у OpenAI: модели тут на 8 и 16 кГц, телефонное
аудио и так приходит на 8 кГц, и заставлять каждого клиента ресемплить до 24 кГц,
чтобы sherpa-onnx вернул их обратно, — потеря качества без смысла. При любой частоте
ресемплинг до частоты модели выполняется на входе.

**Аутентификация.** `Authorization: Bearer <ключ>`, как и везде. Браузер не может
задать заголовок при открытии WebSocket, поэтому ключ можно передать подпротоколом —
`openai-insecure-api-key.<ключ>`, то же написание, что у клиентов OpenAI. Любой скрипт
на странице прочитает ключ, который есть у страницы, — именно это значит «insecure»;
ключ при этом настоящий и проверяется как настоящий.

Отличия от исходного API:

- Модель, метод декодирования и тайминги конца фразы принадлежат серверу. Потоковый
  распознаватель фиксирует всё это при загрузке, поэтому сессия их не выбирает:
  запрос другой модели — ошибка, запрос других таймингов — предупреждение.
  `turn_detection: null` при этом выполняется: это значит «границу фразы задаю я сам
  командой commit» — так работает push-to-talk.
- `prompt` игнорируется, с предупреждением. В офлайновом API он отображается в
  hotwords; смещение потокового распознавателя потребовало бы второй резидентной
  копии модели на каждый список слов.
- Каждое событие `delta` несёт ещё и полную гипотезу в объекте `nanoasr`. Потоковый
  декодер не только дополняет, но и переписывает — он может отозвать уже отправленное
  слово, а никакая последовательность дельт этого не выражает. Авторитетное значение —
  полный текст.
- В `completed` есть `nanoasr.start_ms`, `nanoasr.end_ms`, модель и, если модель даёт
  тайминги токенов, `nanoasr.words`.
- Нет временных токенов (ephemeral tokens), нет событий диалога и нет модели, которая
  отвечает.
- Транскрипт без пунктуации и заглавных букв, если их нет в словаре модели, — а так
  обстоит дело со всеми потоковыми русскими моделями. Объект сессии об этом сообщает,
  офлайновые эндпоинты пунктуацию по-прежнему ставят.

Одна сессия — это одно состояние декодера, и `realtime.max_sessions` ограничивает их
число; соединение свыше закрывается с кодом `1013 Try Again Later`, а не ставится в
очередь: сессия, которая начнётся через девяносто секунд, для человека с включённым
микрофоном хуже той, которая не начнётся вовсе. Клиент, отставший больше чем на
`realtime.max_buffered_seconds`, получает об этом сообщение и закрывается — вместо
того чтобы его аудио потерялось, оставив в транскрипте никак не помеченную дыру.

### `era` — совместимость с whisper-asr-webservice

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/asr` | Синхронное распознавание, ответ файлом |
| `POST` | `/detect-language` | Определение языка |
| `POST` | `/asr_task` | Постановка задачи, возврат идентификатора |
| `GET` | `/asr_task/{task_id}` | Опрос состояния и получение результата |

Файл передаётся в поле `audio_file`, остальные параметры — в строке запроса: `encode`,
`task`, `language`, `initial_prompt`, `vad_filter`, `word_timestamps`, `diarize`,
`min_speakers`, `max_speakers`, `output`.

Форматы `output`: `txt` (по умолчанию), `vtt`, `srt`, `tsv`, `json`. Все передаются с
типом `text/plain` и заголовками `Asr-Engine` и `Content-Disposition`.

Эталонный сервис формирует эти форматы по-разному в зависимости от выбранного движка.
Здесь воспроизводится **whisperx** — движок, на котором работает замещаемый сервис.

Тела ответов повторяют этот сервис, а не нативный результат:

- `txt` — строка на сегмент, с префиксом `[spk_0]: ` при диаризации.
- `tsv` — строка заголовка `start`, `end`, `text`, далее целые миллисекунды по сегментам.
- `srt` и `vtt` — реплики собираются из слов, а не из сегментов. Границы сегментов реплику
  не разрывают: слова копятся, пока промежуток между началами двух соседних слов не
  превысит три секунды, а реплика занимает самый широкий интервал, покрытый её словами.
  SubRip нумерует реплики и всегда пишет часы, WebVTT опускает их до первого часа.
- `json` —
  `{"segments": [{"start", "end", "text", "words": [{"word", "start", "end", "score"}]}],
  "word_segments": [...], "language": "..."}`, где `start`, `end` и `score` округлены до
  трёх знаков, как их округляет выравниватель whisperx.

Слова присутствуют всегда, независимо от `word_timestamps`: эталон выравнивает каждый
запрос. Модели, не сообщающие достоверность по словам, дают `score` равный 0 и
предупреждение `word_confidence_unavailable`. Модель, не дающая потоковых меток времени,
даёт одно слово на сегмент во всю его длину — это предупреждение
`word_timestamps_unavailable`.

Ошибки принимают одну из двух форм, предусмотренных контрактом. Запрос, не прошедший
сигнатуру эндпойнта — отсутствующий `audio_file`, испорченный параметр, — это `422` со
списком FastAPI: `{"detail": [{"loc": ["body", "audio_file"], "msg": "field required",
"type": "value_error.missing"}]}`. Всё остальное сохраняет объект, который эталон
возбуждает вручную: `{"detail": {"message": "task not found"}}`, с дополнительными полями
`code` и `param`.

Отличия от оригинального сервиса:

| Параметр или поведение | Реализация в NanoASR |
|---|---|
| `task=translate` | `501`, модели перевода не поставляются |
| `initial_prompt` | Список hotwords через запятую |
| `encode`, `vad_filter` | Принимаются, не влияют на результат: задаются конфигурацией сервера |
| `min_speakers`, `max_speakers` | Сводятся к точному числу говорящих; диапазон отбрасывается |
| `task_id` | Идентификатор задачи с суффиксом запрошенного формата |
| `Asr-Engine` | Сообщает `nanoasr`; эталон отдаёт своё значение `ASR_ENGINE`, то есть `whisperx` |
| `GET /` | Не обслуживается: перенаправление на `/docs` не реализовано |
| Аутентификация | Обязательна, как и для остальных диалектов |

Значение `output` вне опубликованного перечисления отдаётся как `txt`, а не отклоняется:
эталон объявляет это перечисление в своём документе OpenAPI и никак его не проверяет,
поэтому запрос, на который он отвечал, получает ответ и здесь. Настройки ширины строки
субтитров, которые эталон читает из окружения (`SUBTITLE_MAX_LINE_WIDTH`,
`SUBTITLE_MAX_LINE_COUNT`), воспроизведены в значениях по умолчанию — именно они задают
упомянутый выше разрыв реплики по трёхсекундной паузе.

Поля для предупреждений в этом контракте отсутствуют, поэтому сведения о применённых
ограничениях передаются в заголовке `X-NanoASR-Warnings` в виде списка кодов.

`/detect-language` возвращает язык, объявленный разрешившейся моделью распознавания.
Поле `confidence` равно `1`, если модель поддерживает единственный язык, и `0`, если
языков несколько и выбран первый. Модель идентификации языка в поставку не входит.

## Настройки распознавания

### `channel_mode` — обработка каналов

| Значение | Поведение |
|---|---|
| `downmix` (по умолчанию) | Каналы усредняются в одну дорожку |
| `first` | Используется нулевой канал, остальные отбрасываются |
| `split` | Каждый канал распознаётся отдельно, результаты объединяются по времени |

`split` предназначен для стереозаписей, в которых собеседники разведены по каналам
(телефонная запись A/B leg). Каждый сегмент и каждое слово содержат поле `channel`,
что даёт разделение говорящих без диаризации и точнее её. Диаризация при `split` не
выполняется и возвращает предупреждение `diarization_skipped_split`.

`first` отбрасывает остальные каналы полностью и применим, когда второй канал заведомо
не содержит речи.

В режиме `split` каждый канал декодируется целиком, поэтому объём памяти умножается на
число каналов. Верхняя граница задаётся параметром `audio.max_split_channels`
(по умолчанию 2); файл с бо́льшим числом каналов отклоняется с кодом `400`.

### `decoding_method` — метод декодирования

| | `greedy_search` | `modified_beam_search` |
|---|---|---|
| Семейства моделей | Все | Только `transducer` |
| Принцип | На каждом шаге выбирается наиболее вероятный токен | Параллельно рассматривается `max_active_paths` гипотез |
| Относительная стоимость | Базовая | +29 % при 4 путях, +57 % при 8 путях |
| Поддержка hotwords | Нет | Требуется |

`greedy_search` применяется по умолчанию. `modified_beam_search` повышает точность на
записях с шумом, узкополосным каналом и редкими именами собственными; на чистом
материале разница в тексте может отсутствовать.

Модели CTC перебор гипотез не поддерживают. Запрос `modified_beam_search` к такой
модели обслуживается штатным методом и сопровождается предупреждением
`decoding_method_unavailable`.

`decoding_method` и `max_active_paths` фиксируются при загрузке распознавателя, поэтому
их изменение на уровне запроса требует второго резидентного экземпляра модели. Бюджет
задаётся параметром `asr.variants.max`; при нулевом значении запрос обслуживается
настройками модели с соответствующим предупреждением.

### `hotwords` — смещение распознавания

Список слов и фраз, вероятность которых повышается при декодировании: имена
собственные, названия организаций, терминология. Механизм изменяет вероятности, а не
словарь: слово из списка может не появиться в результате либо появиться ошибочно.

Условия применения:

1. Семейство модели — `transducer`.
2. `decoding_method: modified_beam_search`.
3. Единица моделирования допускает токенизацию фразы: `cjkchar` — без дополнительных
   файлов, `bpe` и `cjkchar+bpe` — при наличии `bpe_vocab` в манифесте модели.

Рекомендуемый объём списка — десятки фраз. Ограничение определяется точностью, а не
производительностью: чем длиннее список, тем чаще смещение срабатывает на неверных
позициях. В список следует включать только те фразы, которые модель действительно
распознаёт неверно.

Список входит в ключ пула моделей: каждый уникальный набор hotwords требует отдельного
резидентного экземпляра. Механизм предназначен для стабильного словаря, а не для
параметра, изменяющегося от запроса к запросу.

```yaml
asr:
  variants:
    max: 1
    allow_hotwords: true
postproc:
  hotwords:
    enabled: true
    default_score: 1.5
```

`hotwords_score` определяет силу смещения; рабочий диапазон — 1.5–2.0. В диалекте
OpenAI список передаётся через `prompt` без значения, и применяется
`postproc.hotwords.default_score`.

Модели встроенного каталога перечисленным условиям не удовлетворяют: русские модели
используют `char` либо подслова без словаря. Для работы механизма требуется запись
каталога с файлом `bpe_vocab`.

## Диаризация

Диаризация выполняется вторым проходом по всей записи. Бэкендов два.

**`sortformer`** (по умолчанию) — [Nemotron-3-Diarization](https://huggingface.co/nvidia/Nemotron-3-Diarization):
одна сквозная модель, которая сама размечает до восьми говорящих прямо по звуку, в порядке
их первого появления. Кластеризации нет, поэтому настраивать нечего — но и число
говорящих ей сообщить нельзя.

**`sherpa`** — конвейер sherpa-onnx: модель сегментации определяет границы реплик,
модель эмбеддингов преобразует фрагменты в векторы голоса, кластеризация объединяет
фрагменты одного говорящего. Это бэкенд, принимающий точное число говорящих.

В обоих случаях результат содержит поля `speaker` и `speaker_confidence` на уровне слов
и сегментов, а также сводку `speakers[]` с длительностью речи и числом сегментов.
Сегменты разрезаются по границам реплик, короткие фрагменты поглощаются соседними.

```yaml
diarization:
  enabled: true
  backend: sortformer            # или sherpa
  model: nemotron-3-diarization  # sortformer: запись каталога
  # только для sherpa:
  segmentation_model: pyannote-segmentation-3
  embedding_model: campplus-sv-zh-en
  clustering:
    num_clusters: 0
    threshold: 0.85
  min_duration_on: 0.3
  min_duration_off: 0.5
```

| Параметр | Бэкенд | Назначение |
|---|---|---|
| `backend` | | `sortformer` или `sherpa` |
| `model` | sortformer | `nemotron-3-diarization` или `nemotron-3-diarization-int8` |
| `segmentation_model` | sherpa | Модель определения границ реплик |
| `embedding_model` | sherpa | Модель векторного представления голоса |
| `clustering.num_clusters` | sherpa | Фиксированное число говорящих; `0` — кластеризация по порогу |
| `clustering.threshold` | sherpa | Порог косинусного расстояния при неизвестном числе говорящих |
| `min_duration_on` | sherpa | Минимальная длительность реплики, с |
| `min_duration_off` | sherpa | Минимальная длительность паузы между репликами, с |

Модель sortformer (~180 МБ загрузки, ~500 МБ в памяти) скачивается и загружается в фоне
при старте сервера или командой `nanoasr models pull -configured`. Сервер, который не
может её получить, всё равно запускается; запросы с диаризацией тогда получают
транскрипт и предупреждение `diarization_unavailable` с командой, которая это исправит.
Одна копия модели обслуживает все параллельные задачи, а отменённый запрос прекращает
проход за доли секунды — sherpa так не умеет.

`nemotron-3-diarization-int8` — та же модель с весами в int8: тот же DER на стенде ниже и
проход примерно в 1,5 раза быстрее, но только на процессорах с VNNI (AVX-512 VNNI или
AVX-VNNI); на остальных может быть медленнее. Включается только явно.

**Число говорящих.** Параметр запроса `num_speakers` задаёт число говорящих для
конкретного файла. С `sherpa` кластеризация режется ровно на столько говорящих — что не
гарантирует результата: дендрограмма режется по числу листьев, и один из них может
достаться выбросу. Для `sortformer` это не входной параметр: модель решает сама, а ответ
содержит предупреждение `diarization_fewer_speakers` или `diarization_more_speakers`,
если найдено не столько, сколько запрошено. Больше восьми говорящих — только
`backend: sherpa`.

**Обновление с 1.0.4 и раньше.** Конфигурация без ключа `backend` получает `sortformer`.
Ключи `clustering` и `min_duration_*` при этом не действуют, и если они отличаются от
значений по умолчанию, сервер сообщает об этом при запуске. `backend: sherpa` в точности
возвращает прежнее поведение. Установщики скачивают новую модель при обновлении.

### Что измерено

В репозитории есть эталонный стенд: `make diar-testdata` собирает 16 минут
русского диалога двух человек из корпуса
[Dialogs](https://huggingface.co/datasets/langswap/dialogs-ru-emotional-conversations)
с точной разметкой границ реплик, `make diar-eval` считает **DER** — долю
времени, отнесённую не тому говорящему, пропущенную или выдуманную. Время —
четыре ядра Xeon 2,8 ГГц.

| Бэкенд | Конфигурация | Найдено говорящих | DER | Время на 16 мин |
|---|---|---|---|---|
| `sortformer` | `nemotron-3-diarization` | 2 | **1.4 %** | 32 с |
| `sortformer` | `nemotron-3-diarization-int8` | 2 | **1.4 %** | 21 с |
| `sherpa` | `campplus-sv-zh-en`, `num_speakers=2` | 2 | 2.9 % | 134 с |
| `sherpa` | `campplus-sv-zh-en`, порог 0.85 | 6 | 5.9 % | 136 с |
| `sherpa` | `campplus-sv-zh-en`, порог 0.50 | 36 | 71.6 % | |
| `sherpa` | `campplus-sv-voxceleb`, `num_speakers=2` | 2 | 40.3 % | |
| `sherpa` | `wespeaker-voxceleb-resnet34`, `num_speakers=2` | 2 | 47.5 % | |

Все 1.4 % у sortformer — пропущенная речь на краях реплик; говорящих она не путает, и ей
ничего не сообщали. У sherpa сегментация работает — пропуск речи 0.8 % и ложная тревога
0.5 % во всех конфигурациях, — а весь остальной DER даёт кластеризация: порог sherpa-onnx
по умолчанию 0.5 раскладывает диалог двух человек на 36 «спикеров», все модели
эмбеддингов улучшаются с ростом порога (отсюда 0.85 по умолчанию), а известное
`num_speakers` — её самый сильный рычаг.

Замер сделан на одном студийном диалоге. Это лучшая отправная точка, чем догадки, но не
универсальная константа: на своём материале прогоните `make diar-eval`, выбирая строку
через `DIAR_BACKEND=sortformer` или `DIAR_MODEL=nemotron-3-diarization-int8`.

### Если все реплики достались одному спикеру

1. `channel_mode: split`, если говорящие разведены по каналам — точнее любой
   диаризации и дешевле.
2. С `sherpa`: передать `num_speakers`, если число говорящих известно; понизить
   `clustering.threshold`, если два человека слились в одного, повысить — если один
   разбился на нескольких.
3. С `sortformer` настраивать нечего; для голосов, которые она не различает,
   попробуйте `backend: sherpa` с `num_speakers`.

Частота дискретизации моделей диаризации сверяется с `audio.target_sample_rate`
при запуске; расхождение приводит к отказу в запуске.

**Потоковое распознавание по websocket**

В Node 22 и новее WebSocket-клиент встроен, так что ставить ничего не нужно:

```js
// node stream.mjs call.wav   — 16-битный моно PCM, любая частота
import { readFileSync } from "node:fs";

const ws = new WebSocket("ws://localhost:8080/v1/realtime?intent=transcription", [
  "realtime", `openai-insecure-api-key.${process.env.KEY}`,
]);

ws.addEventListener("open", async () => {
  ws.send(JSON.stringify({
    type: "transcription_session.update",
    session: { input_audio_format: { type: "audio/pcm", rate: 16000 } },
  }));
  // По 100 мс 16 кГц 16 бит моно, как отдавал бы микрофон.
  const pcm = readFileSync(process.argv[2]).subarray(44);
  for (let at = 0; at < pcm.length; at += 3200) {
    ws.send(pcm.subarray(at, at + 3200));
    await new Promise((r) => setTimeout(r, 100));
  }
  ws.send(JSON.stringify({ type: "input_audio_buffer.commit" }));
});

ws.addEventListener("message", (e) => {
  const ev = JSON.parse(e.data);
  if (ev.type === "conversation.item.input_audio_transcription.delta") {
    process.stdout.write(ev.delta);               // либо ev.nanoasr.text — целиком
  } else if (ev.type === "conversation.item.input_audio_transcription.completed") {
    console.log(`\n--- ${ev.transcript}`);
    ws.close();
  }
});
```

Python SDK OpenAI говорит на том же протоколе — и это ровно та программа, на которой
диалект проверяется:

```python
import base64, wave
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8080/v1", api_key=KEY)
with wave.open("call.wav") as w:                  # 16 бит, моно
    rate, pcm = w.getframerate(), w.readframes(w.getnframes())

with client.realtime.connect(model="t-one-ctc-ru") as conn:
    conn.session.update(session={
        "type": "transcription",
        "audio": {"input": {"format": {"type": "audio/pcm", "rate": rate}}},
    })
    for at in range(0, len(pcm), rate // 5):      # по 200 мс
        conn.input_audio_buffer.append(
            audio=base64.b64encode(pcm[at:at + rate // 5]).decode())
    conn.input_audio_buffer.commit()

    for event in conn:
        if event.type == "conversation.item.input_audio_transcription.delta":
            print(event.delta, end="", flush=True)
        elif event.type == "conversation.item.input_audio_transcription.completed":
            print("\n" + event.transcript)
            break
```

Отправлять быстрее реального времени, как в этом цикле, можно: сервер притормаживает
соединение до скорости декодирования, а не теряет аудио, — так что realtime-API
годится и как быстрый способ распознать файл. `commit` дожидается всего, что было
отправлено до него.

## Реестр моделей

Веса моделей не входят в поставку и загружаются на целевую машину. Каждая запись
каталога закреплена по URL, размеру и контрольной сумме SHA-256; загруженные файлы
проверяются перед использованием.

```bash
nanoasr models catalog                       # доступные записи каталога
nanoasr models list                          # установленные модели
nanoasr models pull gigaam-v3-ctc-punct-ru   # загрузка
nanoasr models inspect ./my-model --probe sample.wav
```

`models inspect` определяет семейство и словарь модели, извлекает метаданные из файлов
`.onnx` и формирует черновик манифеста для добавления модели в реестр. Флаг `--probe`
проверяет каждое значение `features.dim` в отдельном процессе.

Модели загружаются в память по требованию, вытесняются по LRU и подлежат горячей замене.
Одновременная резидентность ограничивается параметрами `asr.max_resident_models` и
`asr.max_model_rss_mb`.

### Модели по умолчанию

`nanoasr init` загружает три модели, достаточные для полного цикла обработки
русской речи:

| Идентификатор | Назначение | Размер |
|---|---|---|
| `gigaam-v3-ctc-punct-ru` | Распознавание, русский, со знаками препинания и регистром | 163 МБ |
| `silero-vad-v5` | Определение речевой активности | 0,6 МБ |
| `nemotron-3-diarization` | Диаризация | 176 МБ |

Модели бэкенда `sherpa` (`pyannote-segmentation-3`, `campplus-sv-zh-en`) названы в
конфигурации, но скачиваются, только если выбрать этот бэкенд:
`nanoasr models pull -configured`.

Модель распознавания по умолчанию расставляет знаки препинания и заглавные буквы
самостоятельно, поэтому отдельная модель пунктуации для русского языка не требуется.

### Встроенный каталог

| Идентификатор | Тип | Язык | Размер | Коммерческое использование |
|---|---|---|---|---|
| `gigaam-v3-ctc-punct-ru` | Распознавание, CTC | ru | 163 МБ | Уточняется |
| `gigaam-v3-rnnt-punct-ru` | Распознавание, transducer | ru | 170 МБ | Уточняется |
| `gigaam-v2-ctc-ru` | Распознавание, CTC | ru | 167 МБ | Уточняется |
| `gigaam-v2-rnnt-ru` | Распознавание, transducer | ru | 172 МБ | Уточняется |
| `zipformer-small-en` | Распознавание, transducer | en | 112 МБ | Разрешено |
| `t-one-ctc-ru` | Потоковое распознавание, CTC, 8 кГц | ru | 128 МБ | Разрешено |
| `streaming-zipformer-small-ru` | Потоковое распознавание, transducer | ru | 90 МБ | Уточняется |
| `silero-vad-v5` | Определение речи | multi | 0,6 МБ | Разрешено |
| `nemotron-3-diarization` | Диаризация | multi | 176 МБ | Разрешено |
| `nemotron-3-diarization-int8` | Диаризация, int8 | multi | 89 МБ | Разрешено |
| `pyannote-segmentation-3` | Сегментация говорящих | multi | 7 МБ | Разрешено |
| `campplus-sv-voxceleb` | Эмбеддинги говорящих | multi | 30 МБ | Разрешено |
| `campplus-sv-zh-en` | Эмбеддинги говорящих | multi | 28 МБ | Разрешено |
| `wespeaker-voxceleb-resnet34` | Эмбеддинги говорящих | multi | 27 МБ | Разрешено |

Значение «уточняется» означает, что архив модели не содержит текста лицензии в
машиночитаемом виде. Параметр `registry.strict_license` запрещает загрузку весов,
коммерческое использование которых не подтверждено.

Две потоковые записи обслуживают только `/v1/realtime`: у потокового экспорта нет
декодера для целого файла, и офлайновые эндпоинты отказываются его принимать с
соответствующим сообщением. Ни одна из них не ставит пунктуацию и заглавные буквы —
среди потоковых русских моделей таких нет. `t-one-ctc-ru` — телефонная, 8 кГц,
обучена на записях колл-центра, то есть на той же задаче, для которой выбрана
офлайновая модель по умолчанию; `streaming-zipformer-small-ru` — 16 кГц, в полтора
раза дешевле по памяти и измеренные 0,03x реального времени на двух потоках CPU
против 0,075x у T-one.

Каталог расширяется собственными записями через `registry.catalog_url`, зеркала
задаются параметром `registry.mirrors`.
